# Counter

A minimal contract that stores a single integer counter in instance storage.
It demonstrates the three core storage operations — read, write, and reset —
and serves as the **reference example for the snippet-drift convention**
introduced in Phase 8 (issue #644).

## Snippet-drift convention

Every Rust fence that carries a `src=` attribute in its info string is
treated as a direct copy of the referenced file under `examples/`. CI runs
`scripts/check-snippet-drift.sh` to verify that the snippet has not drifted
from its source. If the two differ, the check fails and the PR is blocked.

```
```rust src=counter/src/lib.rs
```

The path is always relative to the `examples/` directory.

```rust src=counter/src/lib.rs
// SPDX-License-Identifier: MIT
// Copyright (c) 2026 Soroban Cookbook
#![no_std]
use soroban_sdk::{contract, contractimpl, Env};

const COUNTER_KEY: &str = "count";

#[contract]
pub struct Counter;

#[contractimpl]
impl Counter {
    /// Increment the counter by one and return the new value.
    pub fn increment(env: Env) -> u32 {
        let count: u32 = env.storage().instance().get(&COUNTER_KEY).unwrap_or(0);
        let new_count = count + 1;
        env.storage().instance().set(&COUNTER_KEY, &new_count);
        new_count
    }

    /// Return the current counter value without modifying state.
    pub fn get(env: Env) -> u32 {
        env.storage().instance().get(&COUNTER_KEY).unwrap_or(0)
    }

    /// Reset the counter to zero.
    pub fn reset(env: Env) {
        env.storage().instance().set(&COUNTER_KEY, &0_u32);
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use soroban_sdk::Env;

    #[test]
    fn test_initial_value_is_zero() {
        let env = Env::default();
        let contract_id = env.register(Counter, ());
        let client = CounterClient::new(&env, &contract_id);

        assert_eq!(client.get(), 0);
    }

    #[test]
    fn test_increment_increases_count() {
        let env = Env::default();
        let contract_id = env.register(Counter, ());
        let client = CounterClient::new(&env, &contract_id);

        assert_eq!(client.increment(), 1);
        assert_eq!(client.increment(), 2);
        assert_eq!(client.increment(), 3);
    }

    #[test]
    fn test_reset_returns_to_zero() {
        let env = Env::default();

        let client = CounterClient::new(&env, &contract_id);

        client.increment();
        client.increment();
        assert_eq!(client.get(), 2);

        client.reset();
        assert_eq!(client.get(), 0);
    }

    #[test]
    fn test_get_does_not_change_state() {
        let env = Env::default();
        let contract_id = env.register(Counter, ());
        let client = CounterClient::new(&env, &contract_id);

        client.increment();
        assert_eq!(client.get(), 1);
        assert_eq!(client.get(), 1);
    }
}

## Key design decisions

### Instance storage

`instance` storage ties the lifetime of entries to the contract instance
itself. An entry is evicted from the ledger when the instance's TTL expires
and is not extended. For a simple counter that is called frequently this is
the right choice — every invocation naturally extends the TTL.

### Constant key

Using a compile-time `&str` constant (`COUNTER_KEY`) rather than an enum
variant keeps the example minimal. For contracts with many keys, prefer a
`#[contracttype]` enum so the Soroban SDK can derive serialisation.

## Security considerations

:::warning Unaudited example

This pattern is an unaudited teaching example. It is not fit for production
use with real value, and the gaps below are intentional — they keep the
storage mechanics visible. Close them, and get a security review, before you
deploy anything derived from it.

:::

- No access control is applied. Any account can increment, read, or reset the
  counter. Add `require_auth` if you need to restrict who can mutate state.
- `u32` wraps at 4 294 967 295; `overflow-checks = true` in the release
  profile causes the process to abort on overflow in debug builds. In
  production, add explicit bounds checking if overflow is a concern.

### Reentrancy

**Not applicable as written, and that is the point.** None of `increment`,
`get`, or `reset` makes a cross-contract call, and none of them transfer
value, so there is no reentrant call to defend against. Soroban also executes a
single invocation to completion unless a contract deliberately calls into
another contract, which this one never does.

The moment you extend this pattern, the reasoning stops applying. Concretely:

- **If you add a hook or callback** (an oracle push, a reward payout, a
  `transfer` of some minted asset), the callee gets control back in the middle
  of your function. Re-read every value you are about to write _after_ the
  call, or the callee can hand you a stale balance.
- **`reset` is the dangerous one.** It writes `0` to the single key
  `COUNTER_KEY` with no authorization. Paired with any external call added to
  the same function, it becomes a trivial griefing vector — anyone can zero the
  counter mid-operation.
- **Prefer the guard the repo already ships.** The
  Reentrancy Guard pattern sets a storage flag before
  external work and clears it after, so a re-entrant call panics instead of
  corrupting state. Copy that shape rather than hand-rolling a check.
- **`get` is safe to call from anywhere.** It only reads, so it is fine to
  expose as a cross-contract entry point.

In short: this example is reentrancy-free because it is reentrancy-_trivial_.
Keep it that way, or adopt the guard pattern when you extend it.
