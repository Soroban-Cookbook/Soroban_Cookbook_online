# HTLC Atomic Swap Pattern

An atomic swap using Hash Time Lock Contracts (HTLC) enables two parties to exchange assets without trust. This pattern is useful for atomic cross-chain swaps, payment channels, and other decentralized financial interactions.

## Overview

The HTLC pattern relies on three primitives:

- HASH LOCK: The payee claims funds by providing the preimage of a given hash.
- TIME LOCK: Unclaimed funds are returned to the payer after a deadline.
- REFUND: The sender can recover funds if the receiver fails to claim them in time.

```mermaid
  A->>B: Hash claimant created from a preimage.
  A->>A: Deposit funds with hash lock and timeout.
  B->>B: Deposit funds with hash lock and timeout.
  B->>A: Reveals preimage to claim A funds.
  A->>B: Uses preimage to claim B funds.
  note over: If B does not claim, A refunds after timeout.
```

## How it works

The **Hash Time Lock Contract** creates a funding box that locks funds until it either receives the preimage of a given hash or after a specified deadline passes. Here is the step-by-step process:

1. A secret preimage is generated by one party (i.e., A). Its hash is shared.
2. A creates an HTLC script on chain X, funding it with asset A and a timelock.
3. B creates an HTLC script on chain Y, funding it with asset B and a shorter timelock.
4. B claims the funds on chain X by revealing the preimage.
5. A uses that preimage to claim the funds on chain Y.
6. If B draws out, A refunds from chain V after timeout.

## Security Considerations

This pattern carries two important security musts:

- High Confidentiality: The preimage must be known only to the sender and the receiver, as revealing it to a third party could allow them to claim funds.
- Clock Synchronization: The timelocks must be set correctly to avoid one party forfeiting funds unfairly. Whatever activity is more critical should have a long enough buffer.

## Code Example

> **Implementation Note**: The code snippets below present the conceptual interface for HTLC functions. Production implementations require explicit authorization (`require_auth`), strict timelock validations against ledger sequence/timestamp, re-entrancy prevention, and storage TTL management.

- **Authorization Expectations**: Callers initiating swaps or claiming/refunding funds must authenticate via `require_auth()` (e.g. `sender.require_auth()` / `receiver.require_auth()`) to prevent unauthorized claims or premature refunds.
- **Re-entrancy Limits**: Token transfers triggered during claim or refund operations must execute after state mutations (checks-effects-interactions pattern) or be protected by re-entrancy guards to prevent reentrant claim/refund exploits.
- **Storage TTL & Data Expiry**: HTLC entries stored in contract storage (instance or temporary/persistent) are subject to Soroban ledger storage TTL limits. If an HTLC entry expires before the timelock refund period elapses, the entry must be restored via TTL extension before `refund()` can be executed.

## Deploy Notes

When deploying an Application using the Her lock Pattern:

- Ensure the contracts are deployed on the Appropriate networks.
- Set the deadline according to the block time and imaged response delay.
- Monitor chain confirmation times to avoid a one-block reordering attack.
