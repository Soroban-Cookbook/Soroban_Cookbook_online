# Multi-Token Vault

A **multi-token vault** keeps per-user, per-token accounting in a single contract.
Any address may deposit any number of different tokens; the vault records each
balance independently and allows partial or full withdrawals at any time.

## When to use this pattern

- Consolidated custody for DeFi protocols handling multiple assets
- Portfolio or yield-bearing vaults that accept arbitrary tokens
- Any contract that needs to track balances for several tokens without deploying one vault per asset
- Learning how compound storage keys work in Soroban

## Contract overview

```
deposit(depositor, token, amount)
  └─ adds `amount` to Balance(depositor, token) and VaultTotal(token)

withdraw(withdrawer, token, amount)
  └─ deducts `amount` from Balance(withdrawer, token) and VaultTotal(token)
  └─ reverts if balance is insufficient

balance(user, token)
  └─ read-only: returns Balance(user, token), or 0 if never deposited

vault_total(token)
  └─ read-only: returns the sum of all deposits for a token
```

## Storage layout

| Key                    | Type   | Storage  | Description                         |
|------------------------|--------|----------|-------------------------------------|
| `Balance(user, token)` | `i128` | instance | Deposited balance per (user, token) |
| `VaultTotal(token)`    | `i128` | instance | Sum of all balances for a token     |

The compound key `Balance(user, token)` is the core of the pattern — it encodes
both the depositor address and the token address into a single storage entry
without a nested map abstraction.

:::note Instance vs. persistent storage
This example uses `instance` storage for simplicity. A production vault should use
`persistent` storage and extend entry TTLs to ensure balances survive beyond the
default ledger expiry window.
:::

## Full source

```rust title="examples/multi-token-vault/src/lib.rs"
#![no_std]

use soroban_sdk::{contract, contracterror, contractimpl, contracttype, Address, Env};

#[contracttype]
#[derive(Clone)]
pub enum DataKey {
    /// Per-user, per-token deposited balance.
    Balance(Address, Address),
    /// Vault-wide total deposits for a given token.
    VaultTotal(Address),
}

#[contracterror]
#[derive(Copy, Clone, Debug, Eq, PartialEq, PartialOrd, Ord)]
#[repr(u32)]
pub enum Error {
    /// Deposit or withdraw amount must be greater than zero.
    InvalidAmount = 1,
    /// Withdrawal exceeds the caller's recorded balance for that token.
    InsufficientBalance = 2,
}

#[contract]
pub struct MultiTokenVault;

#[contractimpl]
impl MultiTokenVault {
    pub fn deposit(env: Env, depositor: Address, token: Address, amount: i128) -> Result<(), Error> {
        depositor.require_auth();

        if amount <= 0 {
            return Err(Error::InvalidAmount);
        }

        let balance_key = DataKey::Balance(depositor.clone(), token.clone());
        let current: i128 = env.storage().instance().get(&balance_key).unwrap_or(0_i128);
        env.storage().instance().set(&balance_key, &(current + amount));

        let total_key = DataKey::VaultTotal(token);
        let vault_total: i128 = env.storage().instance().get(&total_key).unwrap_or(0_i128);
        env.storage().instance().set(&total_key, &(vault_total + amount));

        Ok(())
    }

    pub fn withdraw(
        env: Env,
        withdrawer: Address,
        token: Address,
        amount: i128,
    ) -> Result<i128, Error> {
        withdrawer.require_auth();

        if amount <= 0 {
            return Err(Error::InvalidAmount);
        }

        let balance_key = DataKey::Balance(withdrawer.clone(), token.clone());
        let current: i128 = env.storage().instance().get(&balance_key).unwrap_or(0_i128);

        if current < amount {
            return Err(Error::InsufficientBalance);
        }

        // Checks-effects: update state before any external interaction.
        env.storage().instance().set(&balance_key, &(current - amount));

        let total_key = DataKey::VaultTotal(token);
        let vault_total: i128 = env.storage().instance().get(&total_key).unwrap_or(0_i128);
        env.storage().instance().set(&total_key, &(vault_total - amount));

        Ok(amount)
    }

    pub fn balance(env: Env, user: Address, token: Address) -> i128 {
        env.storage()
            .instance()
            .get(&DataKey::Balance(user, token))
            .unwrap_or(0_i128)
    }

    pub fn vault_total(env: Env, token: Address) -> i128 {
        env.storage()
            .instance()
            .get(&DataKey::VaultTotal(token))
            .unwrap_or(0_i128)
    }
}
```

## Key design decisions

### Compound storage keys

The `DataKey::Balance(Address, Address)` variant stores both the user address
and the token address inside the enum variant. Soroban serialises the whole
variant — including the embedded addresses — into a single storage key.
This replaces what would be a nested map in other environments with a flat
key-value store entry, which is both simpler and more storage-efficient.

```rust
// One entry per (user, token) pair — no nested maps needed.
let key = DataKey::Balance(user.clone(), token.clone());
let balance: i128 = env.storage().instance().get(&key).unwrap_or(0);
```

### Vault-wide totals

A separate `VaultTotal(token)` key accumulates all deposits for a given token.
This enables O(1) liquidity checks without iterating all user balances.

```rust
let total: i128 = env.storage().instance().get(&DataKey::VaultTotal(token)).unwrap_or(0);
```

### Checks-effects pattern in `withdraw`

State is updated **before** returning the amount to the caller.
This makes the intent explicit and matches best-practice even though
Soroban's execution model already prevents reentrancy at the host level.

### Accounting-only design

The contract records amounts in storage but does not call SAC (Stellar Asset Contract)
`transfer` functions — it is intentionally scoped to teach the multi-asset
accounting pattern without cross-contract complexity. See the
[token-transfer example](./basic-token) for how to wire up actual token movement.

## Extending this example

### Add persistent storage for long-lived vaults

Replace `instance()` with `persistent()` and bump entry TTLs after each mutation:

```rust
env.storage().persistent().set(&balance_key, &new_balance);
env.storage().persistent().extend_ttl(&balance_key, 100_000, 200_000);
```

### Emit events on deposit and withdrawal

```rust
env.events().publish(
    (symbol_short!("deposit"), depositor.clone()),
    (token.clone(), amount),
);
```

### Integrate actual token transfers

Call the SAC `transfer` function to move real assets on `deposit` and `withdraw`:

```rust
// On deposit: pull tokens from depositor into the vault contract.
token_client.transfer(&depositor, &env.current_contract_address(), &amount);

// On withdrawal: push tokens from the vault contract to the withdrawer.
token_client.transfer(&env.current_contract_address(), &withdrawer, &amount);
```

### Add an allowlist

Gate which tokens the vault accepts by maintaining an admin-controlled set of
approved token addresses.
