## Overview

This pattern demonstrates a complete basic token contract implementing three core operations: `mint`, `transfer`, and `balance`. It serves as the foundation for understanding token mechanics in Soroban before advancing to standardized token interfaces like SAC (Soroban Asset Contract).

<PatternCallout variant="info" title="When to use">

Use this pattern to bootstrap a simple token system, understand state management for balances, and grasp authorization patterns. For production, consider using SAC or wrapping existing assets.

</PatternCallout>

<PatternCallout variant="note" title="Teaching Token">
  The `examples/token-transfer` example demonstrates a teaching token implementation. It is **not**
  the Stellar Asset Contract (SAC) used for production assets. For production, refer to the [Stellar
  Asset Contract (SAC)](../concepts/stellar-asset-contract) documentation.
</PatternCallout>

<PatternSection id="prerequisites" title="Prerequisites">

- Rust stable and `cargo`
- Soroban CLI installed ([setup guide](/docs/getting-started/setup))
- Basic familiarity with Soroban contracts and the `soroban_sdk`
- Understanding of `Address` types and authentication

</PatternSection>

<PatternSection id="implementation" title="Implementation">

The contract manages a ledger mapping addresses to token balances using persistent storage. Three public functions allow minting tokens, querying balances, and transferring between accounts.

<PatternCallout variant="warning" title="Unaudited teaching example">

The contract below is an **unaudited educational example**. It has **not** been
through a security review and it is **not fit for production or for holding real
value** — most obviously because `mint` is completely unrestricted, so anyone can
inflate the supply at will.

Read the two limits that matter most before you copy anything:

- **Reentrancy** — none of `mint`, `balance`, or `transfer` makes a cross-contract
  call, so there is no re-entrant call to defend against _as written_. The moment
  you add one (a transfer-fee hook, a mint callback, a cross-chain message), that
  protection is gone. See [Reentrancy limits](#reentrancy-limits).
- **Storage TTL / data expiry** — balances live in `persistent` storage, which
  expires. This example never extends a TTL, so a balance can be **archived and
  then permanently deleted**, silently turning into a zero balance. See
  [Reentrancy and storage TTL limits](#reentrancy-limits).

For a real token, use the [Stellar Asset Contract (SAC)](../concepts/stellar-asset-contract)
or the [SEP-41 standard](../concepts/token-standards) instead of deploying this.

</PatternCallout>

```rust
#![no_std]
use soroban_sdk::{contract, contracterror, contractimpl, contracttype, Address, Env};

/// Storage key for tracking token balances per address.
#[contracttype]
#[derive(Clone)]
pub enum DataKey {
    Balance(Address),
}

/// Error codes for token operations.
#[contracterror]
#[derive(Copy, Clone, Debug, Eq, PartialEq, PartialOrd, Ord)]
#[repr(u32)]
pub enum Error {
    InsufficientBalance = 1,
    InvalidAmount = 2,
    SelfTransfer = 3,
}

#[contract]
pub struct TokenTransfer;

#[contractimpl]
impl TokenTransfer {
    /// Mint tokens to an address (for testing and bootstrapping).
    /// In production, restrict this to authorized minters.
    pub fn mint(env: Env, to: Address, amount: i128) {
        let key = DataKey::Balance(to.clone());
        let current: i128 = env.storage().persistent().get(&key).unwrap_or(0);
        env.storage().persistent().set(&key, &(current + amount));
    }

    /// Query the token balance of an address.
    pub fn balance(env: Env, of: Address) -> i128 {
        let key = DataKey::Balance(of);
        env.storage().persistent().get(&key).unwrap_or(0)
    }

    /// Transfer tokens from sender to recipient.
    /// Requires authorization from the sender address.
    pub fn transfer(env: Env, from: Address, to: Address, amount: i128) -> Result<(), Error> {
        from.require_auth();

        // Validate amount
        if amount <= 0 {
            return Err(Error::InvalidAmount);
        }

        // Prevent self-transfer
        if from == to {
            return Err(Error::SelfTransfer);
        }

        // Check sender has sufficient balance
        let from_key = DataKey::Balance(from.clone());
        let from_balance: i128 = env.storage().persistent().get(&from_key).unwrap_or(0);

        if from_balance < amount {
            return Err(Error::InsufficientBalance);
        }

        // Perform transfer
        let to_key = DataKey::Balance(to.clone());
        let to_balance: i128 = env.storage().persistent().get(&to_key).unwrap_or(0);

        env.storage()
            .persistent()
            .set(&from_key, &(from_balance - amount));
        env.storage()
            .persistent()
            .set(&to_key, &(to_balance + amount));

        Ok(())
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use soroban_sdk::{testutils::Address as _, Env};

    fn setup() -> (Env, TokenTransferClient<'static>) {
        let env = Env::default();
        env.mock_all_auths();
        let contract_id = env.register(TokenTransfer, ());
        let client = TokenTransferClient::new(&env, &contract_id);
        (env, client)
    }

    #[test]
    fn test_mint_increases_balance() {
        let (env, client) = setup();
        let alice = Address::generate(&env);

        client.mint(&alice, &500);
        assert_eq!(client.balance(&alice), 500);
    }

    #[test]
    fn test_transfer_moves_tokens() {
        let (env, client) = setup();
        let alice = Address::generate(&env);
        let bob = Address::generate(&env);

        client.mint(&alice, &1000);
        client.transfer(&alice, &bob, &400);

        assert_eq!(client.balance(&alice), 600);
        assert_eq!(client.balance(&bob), 400);
    }

    #[test]
    fn test_transfer_fails_on_insufficient_balance() {
        let (env, client) = setup();
        let alice = Address::generate(&env);
        let bob = Address::generate(&env);

        client.mint(&alice, &100);
        let result = client.try_transfer(&alice, &bob, &200);

        assert_eq!(result, Err(Ok(Error::InsufficientBalance)));
        assert_eq!(client.balance(&alice), 100);
        assert_eq!(client.balance(&bob), 0);
    }

    #[test]
    fn test_transfer_fails_on_invalid_amount() {
        let (env, client) = setup();
        let alice = Address::generate(&env);
        let bob = Address::generate(&env);

        client.mint(&alice, &100);
        let result = client.try_transfer(&alice, &bob, &0);
        assert_eq!(result, Err(Ok(Error::InvalidAmount)));

        let result = client.try_transfer(&alice, &bob, &-50);
        assert_eq!(result, Err(Ok(Error::InvalidAmount)));
    }

    #[test]
    fn test_self_transfer_is_rejected() {
        let (env, client) = setup();
        let alice = Address::generate(&env);

        client.mint(&alice, &100);
        let result = client.try_transfer(&alice, &alice, &50);
        assert_eq!(result, Err(Ok(Error::SelfTransfer)));
    }

    #[test]
    fn test_initial_balance_is_zero() {
        let (env, client) = setup();
        let alice = Address::generate(&env);

        assert_eq!(client.balance(&alice), 0);
    }
}
```

<PatternSection id="key-concepts" title="Key Concepts">

### Storage Model

Balances are stored in persistent storage using the `Balance(Address)` enum variant as the key. This allows efficient lookups and updates without scanning the entire ledger.

### Authorization

The `transfer` function calls `from.require_auth()` to ensure the transaction is signed by the sender. This prevents unauthorized token transfers.

### Error Handling

Three error codes cover the main failure modes:

- **InsufficientBalance**: Sender doesn't have enough tokens
- **InvalidAmount**: Zero or negative amounts are rejected
- **SelfTransfer**: Transferring to yourself is a no-op and disallowed

### Minting

The `mint` function bypasses authorization checks. In production, restrict minting to authorized parties using a minter role or ownership model.

</PatternSection>

<PatternSection id="reentrancy-and-storage-ttl-limits" title="Reentrancy and storage TTL limits">

These two limits are the difference between a teaching contract and a token that
can safely hold value. Neither is enforced by this example.

### Reentrancy limits

**Reentrancy does not apply as written, and that is the only reason.** `mint`,
`balance`, and `transfer` call `env.storage()` and nothing else — there is no
cross-contract call, no token `transfer`, and no callback, so no external code
ever regains control partway through a state update. Soroban runs an invocation
to completion unless a contract deliberately calls into another contract.

The guarantees you can rely on today, and what breaks them:

- **`transfer` is checks-then-effects.** It reads the sender balance, verifies
  `from_balance >= amount`, and only then writes both sides. That ordering is
  safe _only_ because no untrusted code runs between the read and the write.
- **Adding any external call breaks it.** Insert a transfer-fee hook, a mint
  callback, a cross-chain `invoke_contract`, or a SAC payment between the read
  and the write and the pattern is exploitable: re-read both balances after the
  call, because the callee can move funds or change state in the meantime.
- **`to_balance` is read before the write.** That value can be stale if anything
  external ran in between. Re-read it after any external call.
- **`transfer` does call `from.require_auth()`** — that is an authorization
  check, not a reentrancy guard. It stops unauthorized senders; it does not stop
  a callee re-entering.
- **Use the repo's guard shape.** The
  Reentrancy Guard pattern sets a storage flag before any
  external work and clears it afterwards, so a re-entrant call panics rather than
  double-spending. Adopt it whenever you extend this contract.

### Storage TTL and data-expiry limits

Balances are stored with `env.storage().persistent()`, and **persistent entries
expire.** This is the single most dangerous omission in the example:

- **Nothing here extends a TTL.** There is no `extend_ttl` call anywhere in the
  contract, so each balance entry gets the network's default minimum lifetime and
  then starts counting down.
- **Expiry is two-phase.** When a persistent entry's TTL lapses, the ledger
  **archives** it: reads still succeed but return the archived (stale) value
  while restoration is pending. If it is not restored before the next ledger
  closes the retention window, the entry is **deleted permanently**.
- **A deleted balance reads back as `0`.** Because `balance` uses
  `.unwrap_or(0)`, permanent deletion is indistinguishable from "never had a
  balance". A holder's funds can vanish with no error and no event.
- **Instance storage would not help.** Instance entries expire with the contract
  instance, so a long-idle token loses everything at once.
- **A production token must** extend the TTL on every balance it touches, extend
  it for a minimum window ahead of expiry, restore archived entries on read, and
  bump the TTL thresholds via `extend_contract_instance_ttl` / the appropriate
  storage bumps. See the [Storage TTL / Rent
  pattern](../concepts/storage) and the `storage-ttl` example for the
  threshold-bump pattern to copy.
- **The same clock governs fees.** A TTL bump has to be paid for; budgeting for
  rent is part of running a real token, not an afterthought.

</PatternSection>

<PatternSection id="security" title="Security Considerations">

This is an **unaudited example**. The items below are the gaps it deliberately
leaves open, not an exhaustive audit.

1. **Unrestricted Minting**: The current implementation allows anyone to mint tokens. Add access control using an admin address or authorized minters list before production use.

2. **No Decimal Support**: This basic implementation uses integers only. For real assets, consider implementing a `decimals` field and decimal-aware math.

3. **Supply Cap**: Consider implementing a maximum supply to prevent unlimited inflation.

4. **Allowance/Approval**: For more advanced use cases, implement an approve/transferFrom pattern allowing third parties to move tokens on behalf of the owner.

5. **Reentrancy Limits**: Safe only while the contract makes no cross-contract calls. `transfer` relies on a checks-then-effects ordering that assumes no untrusted code runs between reading the sender balance and writing it. Add a guard from the Reentrancy Guard pattern before adding any external call.

6. **Storage TTL / Data Expiry**: Balances are in `persistent` storage and no TTL is ever extended, so a balance can be archived and then permanently deleted — reading back as `0` via `.unwrap_or(0)`. Extend TTLs on every balance touched, restore archived entries on read, and budget for rent. See [Reentrancy and storage TTL limits](#reentrancy-limits).

</PatternSection>

<PatternSection id="deployment" title="Deployment Guide">

### Build the Contract

```bash
cd examples/token-transfer
cargo build --target wasm32-unknown-unknown --release
```

The compiled WASM binary is located at `target/wasm32-unknown-unknown/release/token_transfer.wasm`.

### Deploy to Testnet

1. **Generate or use an existing account**:

   ```bash
   stellar keys generate --global token-admin
   stellar keys fund token-admin --network testnet
   ```

2. **Deploy the contract**:

   ```bash
   stellar contract deploy \
     --wasm target/wasm32-unknown-unknown/release/token_transfer.wasm \
     --network testnet \
     --source token-admin
   ```

   This returns a contract ID (e.g., `CABC...`).

3. **Interact with the contract**:
   ```bash
   stellar contract invoke \
     --id CABC... \
     --network testnet \
     --source token-admin \
     -- mint \
     --to $(stellar keys address token-admin) \
     --amount 1000
   ```

### Query Balance

```bash
stellar contract invoke \
  --id CABC... \
  --network testnet \
  --source token-admin \
  -- balance \
  --of $(stellar keys address token-admin)
```

### Transfer Tokens

```bash
stellar contract invoke \
  --id CABC... \
  --network testnet \
  --source token-admin \
  -- transfer \
  --from $(stellar keys address token-admin) \
  --to GBBD...your-recipient \
  --amount 100
```

For more details, see the [Deploy to Testnet](/docs/getting-started/deploy-testnet) guide.
