# Cross-Contract Vault Pattern

This pattern demonstrates a small but realistic Soroban layout where a vault contract calls an external token contract. The example is deliberately split into multiple crates/modules so the roles are clear:

- the token contract owns balances and authorization
- the vault contract owns accounting and cross-contract orchestration
- the test module exercises the full call chain end-to-end

## When to use this pattern

Use this pattern when a contract depends on another deployed contract for:

- balance checks and transfers
- price or data feeds
- access control checks delegated to a trusted service
- multi-contract workflows that must remain atomic in a single transaction

This is the same shape used in real DeFi systems: caller contract, callee contract, and explicit failure handling at each boundary.

## File map

```text
examples/cross-contract/
├── Cargo.toml
├── README.md
├── src/
│   ├── lib.rs           # exposes Token and Vault modules
│   ├── token.rs         # callee: balance logic + require_auth
│   ├── vault.rs         # caller: typed client + try_* fallback handling
│   ├── test.rs          # end-to-end deployment and auth assertions
│   └── main.rs          # demo entry point for the example crate
└── target/              # generated by cargo test
```

### Role of each file

| File | Role | Why it matters |
| --- | --- | --- |
| `src/token.rs` | Callee contract | Tracks balances and requires `require_auth()` before transfer or mint flows. |
| `src/vault.rs` | Caller contract | Stores a configured token contract address and invokes `TokenClient` methods. |
| `src/test.rs` | Integration tests | Deploys both contracts in the same `Env`, then verifies deposit, withdrawal, auth, and rollback behavior. |
| `src/lib.rs` | Module wiring | Re-exports the contracts so the tests and the example crate can import them cleanly. |

## Architecture and auth flow

```mermaid
flowchart TD
    U[User] -->|deposit / withdraw| V[Vault Contract]
    V -->|TokenClient::transfer| T[Token Contract]
    U -->|require_auth()| T
    A[Admin] -->|set_emergency_mode / update_token_contract| V
    V -->|validate configured callee| T
    T -->|return success or error| V
    V -->|state update or rollback| V
```

The important pattern is that the callee enforces authorization while the caller enforces the business workflow around that external dependency.

## What the example demonstrates

### 1. Typed cross-contract client

The vault uses the generated client from the token contract:

```rust
let token_client = TokenClient::new(&env, &token_contract);
match token_client.try_transfer(&from, &env.current_contract_address(), &amount) {
    Ok(Ok(())) => { /* success */ }
    Ok(Err(_)) | Err(_) => { /* safe fallback */ }
}
```

This gives compile-time verification of the token interface while still allowing recovery from host-level or contract-level failures.

### 2. State updates before external calls

The vault updates its local ledger state before it invokes the token transfer. That keeps the business accounting consistent even if the external call fails and the transaction is rolled back.

### 3. Recovery with `try_*`

Where a contract failure is recoverable, the vault uses `try_transfer` and `try_risky_operation` instead of allowing an unhandled panic to abort the entire transaction.

### 4. Authorization propagation

The token requires the sender to authorize transfers, and the vault only calls the token after the user or admin has been validated by the surrounding workflow.

## Running the example

From the repository root:

```bash
cargo test --manifest-path examples/cross-contract/Cargo.toml
```

Or run inside the example directory:

```bash
cd examples/cross-contract
cargo test
```

The test suite covers:

- successful deposit and withdrawal flows
- insufficient balance failures
- emergency mode and admin authorization checks
- token validation on initialization / update
- rollback behavior when a callee call fails

## Key tests in the example

```rust
#[test]
fn test_successful_deposit_and_withdrawal() {
    let (env, _token_id, token_client, _vault_id, vault_client, admin) = setup_contracts();

    let user = Address::generate(&env);
    token_client.mint(&user, &1000i128).unwrap();

    vault_client.deposit(&user, &1000i128).unwrap();
    assert_eq!(vault_client.user_balance(&user), 1000);

    vault_client.withdraw(&user, &300i128).unwrap();
    assert_eq!(vault_client.user_balance(&user), 700);
}
```

The tests use the Soroban `Env` sandbox, register both contracts, and assert on the exact state transitions that would occur in production.
